Real User Monitoring (RUM)

Runtime Medium oracle Retrospective

Real user monitoring (RUM) measures how an application performs for people using it: how long pages take to load, how quickly they respond, and where users encounter errors. It captures devices, networks, and interactions that a test lab can miss.

A server can return a successful response while the browser spends seconds blocked on JavaScript or fails to display the result. RUM helps close that gap. Where synthetic monitoring runs a scripted journey, RUM follows the journeys people actually take. It is a client-side form of observability, with the same need to ask whether the data represents the people you meant to observe.

What to measure

Start with what a person can notice. Google’s Core Web Vitals describe three parts of the experience: Largest Contentful Paint (LCP) measures when the largest eligible piece of visible content appears; Interaction to Next Paint (INP) measures responsiveness to qualifying interactions during a visit; Cumulative Layout Shift (CLS) measures unexpected movement of visible content. A page can do well on all three and still display the wrong price.

Google’s guidance calls for evaluating these at the 75th percentile, separately for mobile and desktop. That is the value at or below which 75% of the observations fall. Good values are at most 2.5 seconds for LCP, 200 milliseconds for INP, and 0.1 for CLS. The web-vitals library handles the details of measuring and reporting them. A visit without a qualifying interaction has no INP reading, so keep the observation count for each metric rather than assuming every session contributed one.

Performance is only part of the picture. Collect client errors and the outcomes of important actions, such as completing checkout. Browser timing APIs can help show whether a delay came from fetching an asset or waiting for an API response, though cross-origin timing detail may be restricted. A fast response still needs a check that it contained the right result.

Be explicit about what a rate counts. “Errors per request” and “sessions with an error” answer different questions: one session with twenty exceptions is still one affected session. Likewise, a checkout failure rate needs a definition of an attempt, including how abandoned attempts are counted. Handled failures need their own reporting; uncaught exceptions alone will miss them.

Reading a release

These illustrative readings compare one checkout route over equal time windows. Here, p75 means the 75th percentile:

Release and device Observed sessions Sessions with client errors LCP p75 INP p75
Previous, mobile 10,000 100 (1%) 2.2 s 180 ms
Current, mobile 10,000 600 (6%) 3.4 s 310 ms
Previous, desktop 10,000 100 (1%) 1.4 s 110 ms
Current, desktop 10,000 100 (1%) 1.4 s 110 ms

Mobile users are seeing more errors and slower responses while desktop users are seeing little change. That gives the investigation a place to start. It does not yet establish that the release caused the regression: the browser versions, network conditions, or collection settings may also have changed. The session counts support the error rates; interpreting the percentiles also requires the counts of eligible metric observations.

Keep enough context to follow that lead: the release, route template, browser, device class, and sampling rate. Where possible, use a scoped correlation identifier to connect a client failure to a distributed trace. Raw form fields, query strings, and persistent personal identifiers should not be the price of being able to investigate a slow page.

How it gets gamed

A dashboard can improve because its audience changed. Bots that execute JavaScript can enter browser RUM data, as can your own synthetic checks. Their timings, errors, and repeated journeys can distort the picture of human experience. Label known automation and inspect it separately from human traffic. Bot detection is imperfect: a user-agent filter catches self-declared bots, not every automated browser. Record filter changes so removing traffic cannot quietly pass for a performance improvement.

The opposite problem is losing the people with the worst experience. Script blockers, consent choices, early exits, crashes, or a failed collection endpoint can leave sessions unreported. Compare collection volume with an independent source and investigate sudden drops. A client that went silent has not demonstrated a successful visit.

Even the sessions you retain can mislead. A fast majority can hide a slow device class in an overall average. Keeping every error but only a small sample of successful sessions inflates a naive error rate. Compare the same groups, retain observation counts, and record each session’s chance of being sampled so the rates can be calculated consistently or weighted to account for unequal sampling.

Finally, the definition itself can move. Dropping a slow route, changing metric versions, or reclassifying an error as handled can make the chart look healthier without changing anyone’s experience. Annotate those changes alongside application releases.

Response playbook

First check whether the reading is trustworthy. Did collection volume, bot filtering, sampling, or metric eligibility change? Then narrow the problem to a comparable group of users: the same route, device, browser, and time window across releases. Small samples need caution, and percentiles from separate groups cannot simply be averaged together.

Inspect a few representative failures using sanitized error stacks, performance attribution, and trace links. Look for the point where the experience breaks: rendering, the network, a third-party script, or the API. Use a previously agreed failure budget or performance limit to decide whether to roll back or disable a feature. Canary analysis can use these RUM readings too.

After the fix, check the affected users again. A passing lab run helps explain the repair; recovery in the field shows whether it reached the people who were struggling. Confirm that the readings recovered without those people disappearing from the measured population.

What it cannot detect

RUM cannot observe users who never arrive or clients that never report. It cannot cover unvisited paths, prove accessibility, or establish that a completed purchase had the correct price. Use synthetics to check scripted paths even when traffic is quiet, business invariants to check correct outcomes, and load testing to apply controlled stress.
